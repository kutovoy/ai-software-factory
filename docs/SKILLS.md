# Skills

Agent skills are on-demand instruction bundles discovered from `.opencode/skills/<name>/SKILL.md`.
They are loaded by the `skill` tool; each skill's `description` is what the agent sees before loading.

Two kinds live in this repo:

- **Vendored** — third-party skills copied in, trimmed, and adapted. Provenance and license recorded below.
- **Project-local** — written for this repo (`factory-definition`).

OpenSpec's own workflow skills (`openspec-*`) are installed by the OpenSpec CLI and are **not** vendored
here; they are listed for completeness only.

## How to add a skill

### 1. Format

One directory per skill; the directory name **must** equal the `name` field:

```
.opencode/skills/<kebab-name>/SKILL.md      # plus small supporting files if genuinely needed
```

```yaml
---
name: kebab-name              # required, ^[a-z0-9]+(-[a-z0-9]+)*$, 1–64 chars
description: What it does. Use when …   # required, 1–1024 chars, specific enough to be selected
license: MIT                  # required by our policy, even though optional in the format
compatibility: opencode
metadata:                     # optional string→string map; used here for provenance
  source: https://github.com/owner/repo
  upstream: skills/<name>
  vendored: "YYYY-MM-DD"
  modifications: one line describing what changed
---
```

- `SKILL.md` must be spelled in all caps; frontmatter must start at byte 0.
- Frontmatter fields `allowed-tools`, `permissions` etc. are not enforced by OpenCode 1 — put real
  restrictions in `opencode.json` (`permission.skill`) or the agent's own frontmatter.
- Keep the body **under ~150 lines**. Link to upstream for depth instead of copying reference dumps; a
  skill is a workflow, not a library.
- Discovery: `.opencode/skills/` (project), `~/.config/opencode/skills/` (global), and Claude-compatible
  `.claude/skills/` / `.agents/skills/`. Names must be unique across all of them.

### 2. Review checklist

- [ ] **License is MIT, Apache-2.0, or CC-BY-4.0** and stated in the file. Unclear license → link it in
      the table above as "recommended, not vendored" instead of copying.
- [ ] **Actively maintained** — commits within the last year, issues answered, no "archived" banner.
- [ ] **Not a duplicate** of an existing skill or of OpenSpec's workflow. Overlap is a maintenance cost.
- [ ] **Read the whole thing before copying.** Skills are instructions executed with your permissions:
      reject anything that exfiltrates data, runs unexplained shell, fetches remote content at load time,
      or tells the agent to ignore project rules / approvals.
- [ ] No bundled scripts or binaries unless justified and reviewed; no secrets, tokens, or internal URLs.
- [ ] Trimmed to the repo's needs; commands and paths adapted to Bun/TypeScript and this repo's layout.
- [ ] Frontmatter `name` matches the directory; `description` says *when* to use it, not just what it is.
- [ ] Added to the table above with source URL, license, date, and a one-line modification note.

### 3. Then

Run `ls .opencode/skills` and confirm the skill appears in the `skill` tool's available list. If it does
not: check the filename casing, that `name` and `description` are present, that the name is unique, and
that no `permission.skill` rule denies it.

> Reminder: skills are instructions, not a sandbox. The real guarantees come from permissions, runners,
> and the fact that tool execution never happens in the web process.
