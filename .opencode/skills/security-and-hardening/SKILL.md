# Security and Hardening

## Overview

Treat every external input as hostile, every secret as sacred, every authorization check as mandatory.
Security is a constraint on every line that touches user data, auth, or external systems — not a phase.

## When to Use

- Anything accepting user input; auth or authorization; storing or transmitting sensitive data
- Integrating external APIs, webhooks, uploads; handling PII
- Reviewing **agent-generated** code before merge (the common case in this repo)
- Auditing dependencies or supply-chain risk

## Threat Model First (five minutes)

Controls bolted on without a model are guesses.

1. **Map trust boundaries.** HTTP, forms, uploads, webhooks, third-party APIs, queues, **LLM output**,
   and local-looking values: another process's argv/env, filenames on a shared volume, a path in a job
   payload. Trust follows who *wrote* a value, not which channel delivered it.
2. **Name the assets:** credentials, PII, payment data, admin actions, money movement.
3. **Run STRIDE per boundary:** spoofing (authn), tampering (integrity/parameterisation), repudiation
   (audit log), information disclosure (encryption/allowlists), DoS (rate limits, size caps, timeouts),
   elevation (authz, least privilege).
4. **Write abuse cases next to use cases** and make the first one your first test.

## Three-Tier Boundary System

**Always:** validate external input at the boundary; parameterize all queries; encode output; HTTPS
everywhere; hash passwords with bcrypt/scrypt/argon2; security headers; httpOnly+secure+sameSite
cookies; run the native audit against the committed lockfile before release.

**Ask first:** new auth flows or auth logic changes; new classes of sensitive data; new external
integrations; CORS changes; upload handlers; rate-limit changes; elevated permissions.

**Never:** commit secrets; log sensitive data; trust client-side validation as a boundary; disable
security headers; `eval()`/`innerHTML` with user data; keep auth tokens in localStorage; expose stack
traces to users.

## Hardening Controls

- **Injection / XSS / access control:** parameterize every query, never build SQL/shell from strings;
  rely on framework auto-escaping, sanitize raw HTML with an allowlist; authorize **per resource** (the
  authenticated user must own it), not just authenticate.
- **Sessions:** secret from env, bounded `maxAge`, `sameSite` lax/strict (CSRF defence).
- **Headers/CORS:** CSP starts at `default-src 'self'` and is tightened; explicit origin allowlist;
  never `*` with credentials; strip `passwordHash`-style fields before responding; generic error bodies.
- **Validation/uploads:** schema validation at the boundary (shape, length, enum, format) → typed value
  downstream; allowlist MIME, cap size, verify magic bytes. Extensions prove nothing.
- **SSRF:** any user-influenced URL can target internal services. Allowlist scheme/host, resolve all DNS
  records, reject private/reserved ranges (incl. `169.254.169.254`), forbid redirects; pin the IP for
  high-risk surfaces (rebinding TOCTOU).
- **Destructive ops on derived paths:** require all three — resolved target (symlinks resolved) under an
  allowlisted root, at least one level below it, and ownership evidence read before the call. On refusal
  log and stop; never fall back to a broader default path. A shape check proves well-formedness, not
  authorization.
- **Rate limiting:** shared store once more than one process serves traffic (in-memory counters become
  `max × instances`); auth endpoints ~10 attempts / 15 min.
- **Secrets:** from env, `.env.example` committed with placeholders, real `.env*` gitignored, grep the
  staged diff before committing. A secret that reaches a remote is compromised: rotate first, then purge.

## Dependencies and Supply Chain

1. Find the installation boundary and manager (workspace root owning the lockfile). Corroborate
   `packageManager`, lockfile and CI; stop on disagreement or competing lockfiles.
2. Block dependency install scripts before first execution; approve the minimum, commit the policy,
   verify with a frozen install.
3. Run the native audit against the committed lockfile before every release. Triage critical/high by
   **reachability**; never auto-apply forced remediation; document deferrals with reason and review date.
4. Audits only match known advisories — they miss a newly malicious or typosquatted package. Review new
   dependencies, lockfile diffs and script-policy changes together (ownership, maintenance, release age,
   provenance, transitive graph).

## AI / LLM Features

- **Model output is untrusted input.** Never into `eval`, SQL, a shell, `innerHTML`, or a file path.
  Parse defensively, validate against a schema, then encode.
- **Prompts can be hijacked.** Text in context (user message, fetched page, PDF, tool result) can carry
  instructions; the system prompt is not a security boundary — enforce permissions in code.
- **Keep secrets, other tenants' data and the full system prompt out of context.** Scope tool
  permissions, validate every tool argument, confirm destructive actions, cap tokens/rate/recursion.
- Partition RAG embeddings per tenant; validate documents before indexing.

## Agent-Specific Rules

- Agent output is plausible and confident even when insecure. Review it like a hostile contributor.
- A runner executes tools: never let a model-supplied path, URL, or command reach the shell unchecked.
- Secrets are referenced by name in definitions and resolved at run time — never written to logs or
  event streams.

## Common Rationalisations

| Excuse | Reality |
|---|---|
| "Internal tool, security doesn't matter" | Internal tools get compromised; attackers take the weakest link. |
| "We'll add security later" | Retrofitting is ~10x harder. |
| "The framework handles it" | Frameworks give tools, not guarantees. |
| "It's just LLM output, it's only text" | That text can be SQL, a script tag, or a shell command. |
| "The audit passed, so it's safe" | Audits match known advisories only. |

## Red Flags

- Input straight into queries, shells, or HTML rendering
- Secrets in source or commit history; stack traces shown to users
- Endpoints without authz; wildcard CORS; no rate limit on auth
- User-supplied URLs fetched server-side with no allowlist
- LLM output into a query, the DOM, a shell, or `eval`
- Destructive ops guarded only by a path shape check
- Non-reproducible installs, blanket-approved install scripts, competing lockfiles

## Verification

- [ ] Native audit has no unmitigated reachable critical/high findings
- [ ] No secrets in code or history; secret names only, resolved at run time
- [ ] All input validated at boundaries; destructive paths checked per the rule above
- [ ] Authn and authz on every protected endpoint; headers and CORS verified
- [ ] LLM output validated and encoded before use
- [ ] PII classified, minimised, retention-limited, with a working deletion path
